ЛАБОРАТОРНАЯ РАБОТА №4
Настройка Nginx как реверс-прокси и балансировщика нагрузки
Краткий конспект и шпаргалка к защите

============================================================
1. ОБЩАЯ ИДЕЯ: ЧТО МЫ ДЕЛАЕМ
============================================================
В Docker Compose поднимается учебный стенд nginx-load-balancing-lab из 5 контейнеров:

1) nginx (порт 80 на 127.0.0.1) — единая точка входа, реверс-прокси и балансировщик нагрузки.
2) api-1 (порт хоста 8001, внутри Docker 8000) — 1-й экземпляр FastAPI.
3) api-2 (порт хоста 8002, внутри Docker 8000) — 2-й экземпляр FastAPI.
4) api-3 (порт хоста 8003, внутри Docker 8000) — 3-й экземпляр FastAPI.
5) postgres (порт 5432) — одна общая база данных PostgreSQL для всех трех API.

Клиент обращается только на localhost:80. Nginx принимает запрос и сам решает, какому из трех экземпляров api-* его перенаправить.


============================================================
2. ХОД РАБОТЫ ПО ШАГАМ И РЕЗУЛЬТАТЫ
============================================================

ШАГ 1. Подготовка окружения
- Проверяем версии Docker и Docker Compose v2.
- Смотрим структуру файлов (docker-compose-lb.yml, nginx/nginx.conf, nginx/conf.d, scripts/).
- Проверяем синтаксис Compose-файла (docker compose -f docker-compose-lb.yml config --quiet).

ШАГ 2. Запуск и проверка Round Robin (по кругу)
- Собираем и запускаем все 5 контейнеров: up -d --build.
- Ждем статуса healthy.
- Проверяем готовность Nginx: GET /nginx-health -> ответ OK.
- Отправляем 12 запросов на /instance (скрипт check-distribution.sh или цикл curl).
- ИТОГ: запросы распределяются по кругу: api-1, api-2, api-3, api-1...
  В логе nginx/logs/access.log в поле upstream= видно, какой контейнер обработал каждый запрос.

ШАГ 3. Сравнение Round Robin и Least Connections
- Запускаем в фоне 3 долгих запроса (/load/slower) и следом 6 быстрых (/load/fast).
- В nginx/nginx.conf в блок upstream backend_servers первой строкой добавляем: least_conn;
- Проверяем конфиг (nginx -t), пересоздаем контейнер Nginx (--force-recreate), проверяем реальный конфиг внутри контейнера (nginx -T).
- Повторяем тест с долгими и быстрыми запросами.
- ИТОГ: алгоритм Least Connections отправляет новые запросы тому серверу, у которого сейчас меньше всего активных соединений (анализируется по полям upstream и urt в access.log). При равенстве соединений возможен выбор по кругу.

ШАГ 4. Weighted Round Robin (балансировка с весами)
- В блоке upstream задаем веса серверам:
  api-1: weight=3
  api-2: weight=2
  api-3: weight=1
- Пересоздаем контейнер Nginx и отправляем 60 запросов на /instance.
- ИТОГ: запросы распределяются примерно в пропорции 3 : 2 : 1 (около 30, 20 и 10 запросов). Затем возвращаем Round Robin или Least Connections.

ШАГ 5. Пассивные Health Checks и Failover (отказоустойчивость)
- В upstream стоят параметры: max_fails=2 fail_timeout=10s.
- В location / задано:
  proxy_next_upstream error timeout http_502 http_503 http_504;
  proxy_next_upstream_tries 3;
- Искусственно останавливаем первый бэкенд: docker compose ... stop api-1.
- Отправляем 12 запросов на /instance.
- ИТОГ: на первых 1-2 запросах возможна ошибка 502 (если Nginx еще не знает о падении) либо повтор запроса на другом сервере (в access.log тогда видно несколько адресов upstream в одной строке). После 2 сбоев Nginx исключает api-1 на 10 секунд — дальше все запросы без ошибок идут на api-2 и api-3.
- Запускаем api-1 обратно, ждем 10 секунд (fail_timeout), проверяем — api-1 снова в ротации.

ШАГ 6. Замер пропускной способности (утилита hey)
- Сравниваем два варианта:
  1) Через балансировщик (порт 80 -> Nginx -> 3 API).
  2) Напрямую в один экземпляр (порт 8001 -> только api-1).
- Делаем прогрев и по 3 замера для быстрого эндпоинта /load/fast (-n 3000 -c 100).
- Дополнительно сравниваем тяжелый CPU-bound запрос /load/cpu-bound (-n 300 -c 12).
- ИТОГ: получаем таблицу с RPS и временем отклика (latency). На 3 API пропускная способность выше, но не ровно в 3 раза из-за общих узких мест.

ШАГ 7. Завершение работы
- Останавливаем стенд: docker compose -f docker-compose-lb.yml down
  (с флагом -v также удаляются данные PostgreSQL).


============================================================
3. ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ (К ЗАЩИТЕ)
============================================================

1. Что такое реверс-прокси и какие задачи он решает?
Реверс-прокси — это сервер-посредник перед внутренними бэкендами. Клиент обращается только к нему и не знает, какой именно сервер обработал запрос.
Задачи: единая точка входа, скрытие внутренней структуры сети, балансировка нагрузки, настройка HTTPS/TLS в одном месте, логирование, сжатие и кеширование.

2. Зачем конфиг и логи Nginx подключаются через bind mount?
Чтобы редактировать nginx.conf и читать логи прямо с хоста без пересборки образа.
Важный нюанс из лабы: многие редакторы при сохранении перезаписывают файл атомарно (создают новый файл с новым inode). Из-за этого bind mount в контейнере продолжает смотреть на старый файл, и nginx -s reload не подхватывает правки. Поэтому после смены алгоритма контейнер Nginx пересоздают через: docker compose ... up -d --force-recreate nginx, а затем проверяют загруженный конфиг через nginx -T.

3. Чем Round Robin отличается от Least Connections?
- Round Robin (по умолчанию) раздает запросы строго по кругу. Подходит, когда серверы одинаковые и запросы быстрые/однородные.
- Least Connections (least_conn) выбирает сервер с наименьшим числом активных (текущих) соединений. Нужен, когда запросы сильно различаются по длительности — чтобы быстрые запросы не вставали в очередь за долгими.
- Почему один короткий тест не доказывает, что least_conn всегда быстрее? На малой выборке, при быстрых запросах и случайных задержках сети/ОС разница почти незаметна; преимущество least_conn проявляется при высокой параллельной нагрузке и смешанных долгих/коротких запросах.

4. Как работает Weighted Round Robin?
Серверам задается вес (weight=N, по умолчанию 1). Сервер с weight=3 получает в 3 раза больше запросов, чем сервер с weight=1.
- Когда оправдан: если серверы имеют разную производительность (разное железо/лимиты CPU).
- Когда может скрыть проблему: если один из одинаковых серверов начал тормозить из-за бага или утечки памяти, а ему просто урезали вес вместо поиска причины.

5. Когда используют IP Hash (ip_hash)?
Когда нужно закрепить (привязать) клиента к одному и тому же бэкенду по его IP-адресу (например, если приложение хранит данные сессии локально на сервере).

6. Почему приложение желательно делать stateless?
При балансировке каждый новый запрос одного и того же пользователя может попасть на разные экземпляры (сначала api-1, потом api-2). Если приложение не хранит состояние локально в памяти (а держит данные в общей БД PostgreSQL или в Redis), любой экземпляр сможет обработать любой запрос, и их легко масштабировать или перезапускать.

7. Почему нельзя надежно идентифицировать сервис только по IP контейнера?
IP-адреса контейнеров во внутренней сети Docker динамические — при пересоздании или перезапуске контейнера его IP может измениться. Поэтому обращаются по имени сервиса через встроенный Docker DNS (api-1, api-2, api-3), а для проверки возвращают явный ID экземпляра в теле ответа (/instance).

8. Как проверить распределение запросов?
Отправить серию запросов на эндпоинт, возвращающий ID инстанса (/instance), и дополнительно сверить поле upstream= в файле nginx/logs/access.log.

9. Что делают max_fails и fail_timeout?
- max_fails=2: задает число неудачных попыток подряд/за период, после которых сервер считается недоступным.
- fail_timeout=10s: задает и окно времени, за которое считаются ошибки, и длительность (10 секунд), на которую упавший сервер исключается из балансировки. Через 10 секунд Nginx снова попробует отправить на него запрос.

10. Зачем нужен proxy_next_upstream?
Определяет типы ошибок (error, timeout, http_502, http_503, http_504), при которых Nginx не возвращает ошибку клиенту, а автоматически повторяет этот же запрос на другом сервере из группы upstream (не больше proxy_next_upstream_tries раз). Это обеспечивает бесшовный failover для пользователя.

11. Почему повтор запроса опасен для некоторых POST-запросов?
Потому что POST часто является неидемпотентной операцией (меняет состояние, создает заказ, списывает деньги). Если первый бэкенд уже успел записать операцию в базу, но завис и не вернул ответ до таймаута, Nginx повторит запрос на второй бэкенд — в итоге действие выполнится дважды (дубликат заказа или двойное списание). Идемпотентные запросы (GET, PUT, DELETE) при повторе безопасны.

12. Чем пассивные health checks отличаются от активных?
- Пассивные (в бесплатном open-source Nginx): отдельного мониторинга в фоне нет. Nginx узнает о падении бэкенда только по ошибкам реальных пользовательских запросов.
- Активные (в Nginx Plus и других балансировщиках): балансировщик сам по расписанию пингует бэкенды (например, GET /health) и убирает упавший сервер до того, как туда попадут запросы клиентов.

13. Почему 3 экземпляра увеличивают RPS, но не гарантируют ровно 3-кратный рост? Какие есть узкие места?
Балансировка распределяет нагрузку между тремя процессами/воркерами, что особенно помогает на CPU-задачах. Но кратного x3 ускорения почти никогда нет, потому что есть общие ограничения (bottlenecks):
- общий CPU и память хоста / Docker Desktop, где крутятся все 5 контейнеров и сам генератор нагрузки hey;
- сам Nginx (затраты на проксирование);
- общая база данных PostgreSQL (пул подключений, блокировки, диск);
- виртуальная сеть и сокеты хоста.
